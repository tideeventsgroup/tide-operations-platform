# Tide Operations — Architecture

Status: foundation phase. This document is written ahead of the Phase 1
migrations it describes, and is updated as decisions land — it is not
aspirational documentation written after the fact.

## 1. What this is, and what it replaces

Tide Operations is Tide Events Group Scotland's operational platform, built
around one flagship capability: **Tide Incident Control**, the live
event-day command room. Everything else — clients, events, planning,
documents, risk, readiness — exists to feed Incident Control good data and
to turn its output into evidence and client-facing reporting after the
event.

This codebase is a ground-up rebuild. It replaces `tideeventsgroup/tide-operations`
(now `tide-operations-platform`'s predecessor), which remains live at its
existing Vercel deployment untouched during this rebuild. The prior
Supabase project (`tide-operations-system`, `xieckrbngacdxcytsoom`,
`eu-west-2`) is reused for the new schema — its previous data was exported
and the `public` schema was reset; `auth.users` (real staff logins) was left
untouched.

Why rebuild rather than extend: the prior build's document system was
deliberately simplified to an uploaded-file model per an earlier client
decision. The current spec calls for a structured, data-bound Document
Studio, multi-tenant permission scopes, a formal classification scheme,
Major Incident Mode, offline field reporting, and several other structural
changes that touch the data model deeply enough that migrating in place
would cost more than starting clean while keeping the proven stack, brand
system, and several sound architectural patterns (append-only logs, guarded
status-transition RPCs, atomic reference-number counters).

## 2. Stack

- **Next.js 16** (App Router, TypeScript strict, Turbopack). Middleware is
  named `proxy.ts` in this version (`src/proxy.ts`) — not `middleware.ts`.
- **Tailwind CSS v4** + **shadcn/ui (Base UI)** — carried forward wholesale
  from the prior build, including its Tide brand tokens (`--tide-teal`,
  `--tide-charcoal`) and status colour system in `src/app/globals.css`.
- **TanStack Query** for client-side data fetching/mutation state (realtime
  subscriptions, optimistic UI); Server Components and Server Actions remain
  the default for anything that doesn't need it.
- **Supabase**: Postgres 17, Auth, Storage, Realtime, RLS. Project
  `tide-operations-system` (`eu-west-2`, UK/EU data residency).
- **Vercel**: `tide-operations-platform` project, linked to
  `github.com/tideeventsgroup/tide-operations-platform`.

## 3. Domain layer

Business logic does not live in React components or inline in Server
Actions. The shape:

```
src/lib/domain/<entity>-service.ts   — pure(ish) domain functions, one module per entity
src/lib/actions/<entity>.ts          — 'use server' wrappers: auth check, call domain fn, revalidate
src/app/**/page.tsx                  — Server Components; call domain read functions directly
src/components/**                    — presentation; client components call actions or domain reads via TanStack Query
```

Domain functions are reusable from Server Actions, Route Handlers, and (in
Phase 12) background jobs. State-changing operations that must be atomic or
enforce a transition graph (document approval, incident status changes,
event lifecycle changes) are implemented as Postgres RPCs (`SECURITY
DEFINER` functions with their own authorisation checks) and called from the
domain layer — this keeps the invariant enforced even if someone bypasses
the app (direct API call, SQL editor with a scoped role) and keeps the
transition logic in one place instead of duplicated across UI routes. See
`docs/incident-control.md` §"Guarded transitions" for the incident-specific
list.

## 4. Multi-tenancy

```
organisation (Tide Events Group Scotland today; schema supports more)
  └─ clients
       └─ events
            └─ sites → zones → areas → locations
```

Every organisation-scoped table carries `organisation_id`. Every
client-scoped table carries `client_id` (which implies an org via FK).
Every event-scoped table carries `event_id`. All primary keys are UUIDs
(`gen_random_uuid()`); human-readable references (below) are a separate,
immutable, generated column — never the primary key, never used in a join.

## 5. Human-readable identifiers

Format: `<ORG>-<TYPE>[-<YEAR>]-<SEQ>`, e.g. `TEG-EVT-2026-0001`,
`TEG-EVT-2026-0001-INC-0047`, `TEG-CLI-0001`. Generated by a per-type
(optionally per-year) counter table incremented inside the same transaction
as the insert, via a `BEFORE INSERT` trigger — not by counting existing
rows (race-unsafe) and not by application code (same reason). Once
assigned, a reference is immutable — enforced by a trigger that rejects
`UPDATE` on the reference column. This pattern is carried forward from the
prior build, where it worked correctly under concurrent writes.

## 6. Access control

RLS is the access-control boundary, not the UI — every exposed table has
policies; the UI hiding a button is a UX nicety, not a security control.

- `profiles` (1:1 with `auth.users`) carries `account_type` (`pending` |
  `staff` | `client` | `contractor` | ...) — new signups always land as
  `pending`; there is no "first user becomes admin" bootstrap window (an
  admin promotes the first account via SQL once, documented in the repo
  README).
- Granular **role/permission** model, not `isAdmin`: `roles`,
  `permissions`, `role_permissions`, and `event_user_roles` (a user's role
  can differ per event — an Event Controller at one event may be a Deputy
  Controller at another). Permission checks are scope-aware: organisation,
  client, event, module, classification, action (view/create/update/
  assign/approve/issue/resolve/close/reopen/export/administer/redact/
  view-restricted).
- Helper functions (`is_staff()`, `is_admin()`, `has_event_access(event_id)`,
  `has_permission(action, scope_type, scope_id)`, all `SECURITY DEFINER`,
  `STABLE`) are the building blocks every RLS policy composes from, so the
  authorisation logic exists in one place. See `0003_access_helpers.sql`
  once written.
- **Every new `SECURITY DEFINER` function must be locked down explicitly,
  in the same migration, immediately after `CREATE FUNCTION`** — do not
  rely on `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM
  PUBLIC` to suppress it. Postgres grants `EXECUTE` to `PUBLIC` on every
  new function by default, and empirically (tested directly against this
  project, migrations 0007/0009/0010/0020) the default-privilege REVOKE
  does not reliably prevent that grant from being applied to functions
  created in later migrations even by the same role. The safe pattern,
  every time:
  ```sql
  create function my_internal_fn() ... ;
  revoke execute on function my_internal_fn() from public, anon, authenticated;
  grant execute on function my_internal_fn() to authenticated; -- only if genuinely needed client-side
  ```
  Verify with `has_function_privilege('anon', 'my_fn()', 'EXECUTE')` after
  applying, not just by reading the migration.
- Classification (`public` | `client` | `internal` | `confidential` |
  `restricted`, see `docs/data-classification.md`) is enforced both at the
  RLS layer (restricted rows are invisible to non-authorised roles, not
  just hidden in the UI) and, for the most sensitive categories (medical,
  safeguarding), by splitting the sensitive fields into a separate table
  with its own tighter policy rather than a classification column on the
  main row — so a routine `select *` on the parent table cannot leak them.

## 7. Audit

`audit_logs` is append-only (no UPDATE/DELETE policy for anyone except a
service-role maintenance path, logged separately). Populated two ways:
trigger-based capture for schema-level changes on sensitive tables
(permission changes, incident priority/status, document approval/issue,
event lifecycle), and explicit calls from domain functions for actions that
aren't a single row change (export, redaction, restricted-attachment
access, login events forwarded from Supabase Auth webhooks in a later
phase).

## 8. Realtime

Supabase Realtime drives live UI refresh (incident board, event log,
resource status, Major Incident Mode banner). Postgres remains the
authoritative record — Realtime is a refresh signal, not a data source; on
reconnect, clients refetch rather than trust accumulated realtime state.
Welfare/safeguarding records are deliberately excluded from Realtime
channels (see `docs/data-classification.md`).

## 9. Offline / field app (Phase 6)

The mobile field PWA queues incident reports and action responses locally
(client-generated UUID as idempotency key) when offline, with explicit
`Saved locally / Waiting to sync / Syncing / Synced / Sync failed` states
surfaced in the UI — never presented as received by Event Control until the
server has actually acknowledged it. Designed in `docs/incident-control.md`
once Phase 6 starts.

## 10. File security

Supabase Storage, private buckets only, signed URLs issued server-side
after an RLS-backed authorisation check (mirrors the prior build's
`api/documents/[id]/file/route.ts` pattern). No bucket is public.

## 11. Deployment

Vercel (`tide-operations-platform`) ← GitHub (`tideeventsgroup/tide-operations-platform`,
private) ← Supabase (`tide-operations-system`, `eu-west-2`). Environment
variables: see `README.md`. `SUPABASE_SERVICE_ROLE_KEY` must be added
manually via the Supabase/Vercel dashboards — it is never fetched or stored
by tooling that could expose it.
